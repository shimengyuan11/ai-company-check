# WhatsApp 接入方案（评估稿 · 未实施）

> 结论先说：**技术上完全可行，而且是这套工作台最该补的一层**。
> 但真正的工作量不在收发消息，而在会话归属、消息落地和合规。
> 本文记录判断依据、数据模型、五个真实风险与分阶段路径，供后续决定是否动工。

---

## 一、目标：三件事分别能做到什么程度

| 目标 | 可行性 | 依赖什么 |
|---|---|---|
| 在工作台里直接回复消息 | ✅ 完全可行 | 官方 API 发消息；客户最后一条消息后的 24 小时内可自由回复 |
| 来消息自动建档 | ✅ 可行，但要加规则 | webhook 收到未知号码 → 按 `phone_norm` + 尾号 9 位判重建「待分配」线索 |
| 聊天记录全程留档 | ⚠️ 可行但有时间陷阱 | 媒体文件链接**几分钟就过期**，必须在收到 webhook 时立刻下载存库，否则历史里全是裂图 |

## 二、现有系统已经有的地基

不需要重做系统，这套工作台已经是 CRM 骨架了：

- `customers`：`phone` / `phone_norm` / `owner_id` / `stage` —— 建档与防撞单逻辑现成
- `followups`：跟进流，可写可改可删
- `attachments`：已经在往 Postgres 存 bytea（PI / 报价单）
- 权限：客户「各管各的」写在 SQL 层，管理员可见全部，支持移交
- 话术库 + LLM 草稿：现成的差异化能力

要加的只是一张 `messages` 表 + 一套会话视图。

## 三、最小数据模型

```sql
conversations (
  id, wa_id,              -- 客户 WhatsApp 号码（归一化后）
  customer_id,            -- 可空：还没建档时为空
  owner_id,               -- 归属业务员（复用现有"各管各的"权限）
  last_message_at,        -- 列表排序用
  window_expires_at,      -- 24 小时客服窗口到期时间，界面上要显示
  unread_count
)

messages (
  id, conversation_id,
  wa_message_id UNIQUE,   -- 去重关键：Meta 收不到 200 会重投
  direction,              -- in / out
  type,                   -- text / image / document / audio ...
  body,
  media_id, media_path,   -- 媒体必须先落地再存引用
  status,                 -- sent / delivered / read / failed
  created_at
)
```

两个必须记住的点：

1. `wa_message_id` 必须唯一索引。webhook 重复投递是常态，不去重就会重复消息。
2. 媒体下载要在 webhook 处理里同步做完（或立刻入队），不能等用户点开再下。

## 四、计费与规则（来自 Meta 官方文档，2026-10-01 生效版本）

来源：`developers.facebook.com/docs/whatsapp/pricing`（页面更新 2026-09-30）

- 自 2025-07-01 起**按消息计费**：只对「商家发给用户」的消息收费，用户发来的不计费
- 计费只算**送达**的消息；发送失败不收费
- 费率由两件事决定：消息类别 + 接收方国家区号（market）
- 五个类别：marketing / utility / authentication / service / Meta Business Agent
- **非模板消息（普通文本、图片）只能在 24 小时客服窗口内发送**，窗口由用户每条消息开启并重置
- 窗口外只能发**预审批模板**（marketing / utility 类），模板要过审
- 存在「每月服务消息免费额度」与「免费入口点窗口」两种免费情形，具体额度随市场费率卡更新，**接入前必须用官方 rate card 现场核一次**（旧教程里"每月 1000 条免费对话"的规则已废止）

## 五、五个真实风险（按杀伤力排序）

### 1. 号码是资产，封号不可逆

用个人号接 `whatsapp-web.js` / Baileys 这类逆向协议库，是最常见的封号做法，且申诉基本无门。
所有销售对话都在这条线上，一旦被停损失的不是一个功能，是整条渠道。

**结论：只用官方 WABA（Cloud API）。** 代价是需要 Meta Business 账号 + 企业资料 + 号码验证，注册流程繁。

### 2. 计费方式已经变了

不是"接了就能免费聊"。营销类模板按条计费，业务量大时是持续成本。
服务类消息虽然单价低，但也要按市场费率计价。

### 3. 窗口关了就发不出去（这条会直接改变业务流程）

"3/5/7/10 天未联系"筛出来的客户，**全都在 24 小时窗口外**，只能靠模板触达。

产品上必须做出来：

- 界面上标「窗口剩余 X 小时」
- 超窗时把「发送」变成「用模板跟进」，并展示模板审核状态
- 否则业务员点了发不出去，会以为系统坏了

### 4. 现有基础设施撑不住实时 webhook

- Render 免费层 15 分钟无请求即休眠，webhook 打过来要冷启动，Meta 超时会重投
- 需要：常驻实例 + 幂等去重 + 失败重试队列
- Postgres 连接池要按 webhook 并发重新评估（现在是按页面请求设计的）

### 5. 合规与权限要重新想一遍

- 聊天记录含客户个人信息与交易内容，涉及 PIPL / GDPR 的保留期与删除权
- 数据库托管在 Neon，需确认区域与数据出境口径
- 权限：**同一个号码先后被两个业务员接手，历史消息算谁的？** 移交时聊天记录要不要一起转？
- 管理员"能看全部"在聊天场景下意味着能看所有人的对话，界面上要说清楚

## 六、建议的落地顺序

1. **阶段一（1-2 周）**：官方 WABA + webhook 收消息 → `messages` 落库（含媒体即时下载）→ 工作台加「会话」视图 → 一键把号码关联成现有客户。
   **先只做收，不做自动发**，人工在手机 App 回复，工作台负责留档与建档。
2. **阶段二**：开通发送，加 24 小时窗口倒计时、超窗提示、模板管理。
3. **阶段三**：未知号码自动建「待分配」线索 + 分配规则 + 未读红点（复用现有提醒红点机制）。
4. **阶段四**：把话术库 + LLM 草稿接到会话框——"针对这段对话生成一条回复"。
   这是相对通用 CRM 的差异点，前三阶段是基础设施。

## 七、一个必须先定的决策

**公司统一一个 WABA，业务员在内部分配会话；还是每个业务员绑自己的号？**

建议前者：只维护一个号、客户看到的永远是同一个官方号、客户资产不随人离职流失。
代价是所有会话都要经过系统分派，管理成本在公司侧。

后者的好处是业务员用起来没摩擦，坏处是客户跟着人走、人一走渠道也没了。
