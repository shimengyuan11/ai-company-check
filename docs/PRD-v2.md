# PRD · V2：外贸客户工作台（最小版）

> V1 是「AI 公司背调系统」（见 `PRD.md`）——一次性的情报工具。
> V2 把它扩成一个**给外贸业务天天用的客户工作台**：背调变成"客户建档"的入口。
>
> **本文只写第一刀（第 1 期）。** 后面两期见第 9 节，不在本期范围内。

---

## 1. 一句话

给外贸业务一个**快**的客户与跟进记录工具——建档 30 秒、写跟进 10 秒，
人走了、客户转手了，接的人不用去扒聊天记录。

---

## 2. 解决什么问题

- **谁**：外贸业务员（多人，各管各的客户）
- **场景**：每天要建档新线索、记录和客户的每次沟通、翻看某个客户之前聊到哪了
- **现在**：用着另一个 CRM，但**业务原话是"最受不了的就是慢"**——建档慢、写跟进更慢，整理也不方便
- **痛点**：
  - **P1 交接丢上下文**：人走了，接手的人要扒半天聊天记录才知道聊到哪了
  - **P4 慢**：建档、写跟进都慢（**这是第一优先级**）

---

## 3. 三个核心对象

```
用户(User) ──拥有──> 客户(Customer) ──拥有──> 跟进记录(Followup)
                        │
                        └──（第 2 期）附件：PI / 报价单
```

---

## 4. 核心功能（第 1 期，就这 4 个，别加）

1. **登录**（多人各自登录）
2. **客户建档**——字段极少，先存下来，其余后补
3. **写跟进**——一个输入框，敲完回车就存
4. **看客户**——列表 + 详情（这个客户的来龙去脉一屏看完）

---

## 5. 不做（这一期明确不做）

- ❌ 不做**报价单 / PI 的生成**——业务自己会做，系统只做"存下来、找得到"（第 2 期做附件上传）
- ❌ 不做**话术库**——放第 3 期
- ❌ 不做**产品目录 / 配置单**——放第 2 期
- ❌ 不做**全团队共享客户**——本期客户与跟进**默认私有**（见第 7 节）
- ❌ 不做 AI 生成任何东西——本期不含 LLM
- ❌ 不做精美 UI、不做多语言、不做数据抓取

---

## 6. 怎么算做完（验收标准）

打开网址 → 登录 → 建一个客户 → 写一条跟进 → 退出再登录，**数据都还在**。

再加两条**可量化的"快"**（这是本期最要紧的，业务最受不了的就是慢）：

| 动作 | 判据 |
|---|---|
| **建档** | 从打开页面到存下第一个客户，**≤ 30 秒**；**必填字段 ≤ 3 个** |
| **写跟进** | 从打开某个客户到存下一条跟进，**≤ 10 秒**；**只需要一个输入框** |

> 这两条达不到，业务就会退回微信——那这个系统就白做了。

还有一条来自 P1：

> 把一个客户**移交给**同事后，对方**不需要问你**，也能在 3 分钟内看懂这个客户的来龙去脉。

---

## 7. 权限与可见性（本期的安全重点）

**规则**：

| 东西 | 可见性 |
|---|---|
| 客户 + 跟进记录 | **私有**——只有归属人自己看得到 |
| 话术库（第 3 期） | 共享 |
| API key / 额度 | 共享（现状描述，本期不做功能） |

**这里有一个必须正面解决的问题**：

> 客户私有 ⇒ 人走了，接手的人**连看都看不到** ⇒ **P1（交接）反而更严重了**。

所以本期必须有一个动作：**客户移交**（把客户的归属从 A 改成 B）。
**P1 的解药是"移交"，不是"共享"。**

**给未来留的口子**：归属做成**一个字段**（`owner_id`），不是散落在逻辑里。
将来要改成"全团队共享"，只需要改查询条件——**不用重做**。
（业务对这个规则"持保留态度"，所以这一点很重要。）

## 8. 数据字段（一次建表 = 直接照这张表建）

### users（用户）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | SERIAL，主键 | |
| username | TEXT，唯一，非空 | 登录名 |
| password_hash | TEXT，非空 | **哈希**，绝不存明文 |
| display_name | TEXT | 显示名 |
| is_active | BOOLEAN，默认 true | 停用时置 false，不要删用户 |
| created_at | TEXT | UTC |

### customers（客户）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | SERIAL，主键 | |
| owner_id | INTEGER，非空，→ users.id | **归属人**（权限全靠它） |
| company | TEXT，非空 | **必填字段 1** |
| source | TEXT | **必填字段 2**：来源（FB/邮件/展会…），可下拉复用 |
| note | TEXT | **必填字段 3**：一句话备注 |
| country | TEXT | 后补 |
| stage | TEXT | 后补：新线索/已联系/已报价/成交/流失 |
| high_intent | BOOLEAN，默认 false | 高意向标记 |
| created_at / updated_at | TEXT | UTC |

> **只有 3 个必填字段**——这是"建档 ≤30 秒"的直接来源。

### followups（跟进记录）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | SERIAL，主键 | |
| customer_id | INTEGER，非空，→ customers.id | 挂在哪个客户下 |
| user_id | INTEGER，非空，→ users.id | 谁写的 |
| content | TEXT，非空 | **唯一必填字段**——就一个输入框 |
| kind | TEXT，默认 '跟进' | 后补用：跟进 / 需求变化 |
| created_at | TEXT | UTC |

> **只有 1 个必填字段**——这是"写跟进 ≤10 秒"的直接来源。

## 9. 分期（三刀）

### 第 1 期（本文档）
客户建档 + 跟进 + 登录 + 客户移交。

**做法建议**：先**自己用 3~5 天**（登录可以先放最简单的），确认"你真的会天天打开它"，
再放给同事。这类系统**真正的死因不是"同事用不了"，而是"没人用"**。

### 第 2 期 · 少打字
- 表单选项"填写即保存、下次可下拉复用"（**要能合并/停用**，否则会长草）
- 附件上传入口（PI / 报价单）
- 产品目录 / 配置单

### 第 3 期 · 会用 AI
- 话术知识库（模板 + **标签**，不是分类树）+ 针对客户生成触达/阶段话术
- 生成结果**人过一遍再发**（和背调一个原则：AI 出草稿，人负责）

---

## 10. 风险与对策

| 风险 | 对策 |
|---|---|
| **做出来没人用**（最大风险） | 第 1 期死磕"快"；先自己用起来再放给同事 |
| 权限做漏，A 能看到 B 的客户 | 每条查询都带 `owner_id` 过滤；**只靠前端藏按钮不算数** |
| 密码泄露 | 必须哈希；日志里也不打印 |
| 客户私有导致交接更糟 | 本期必须做**客户移交**动作 |
| 移交规则以后要改 | 归属做成字段，改规则只改查询条件 |

## 需求变更记录

### 2026-10-16 · V2 立项（从"情报工具"扩成"客户工作台"）

- **原想法**：业务提了十几条需求（建档 / 跟进 / 话术 / 产品 / 报价 / PI 等）
- **取舍：报价单与 PI 不做生成，只做附件入口**
  - 理由：业务本来就用别的工具做，系统只该补"存下来、找得到"这一环，
    不该抢他们已经顺手的工具。这一刀砍掉了整条最重、风险最高的链
- **取舍：话术不做分类树，改做标签**
  - 理由：来源 / 客户类型 / 场景三个维度会交叉（FB 来的也可能是代理商），
    做成树必然卡在"这条该挂哪个枝"
- **取舍：客户与跟进默认私有**
  - 理由：业务现状是各管各的
  - **但**：私有会加重 P1（交接），所以**必须补"客户移交"**
- **取舍：不强制填完整资料才能建档**
  - 理由：与"快"直接冲突。原则是**先存下来，再慢慢擦亮**
