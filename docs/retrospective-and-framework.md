# 复盘：这个项目是怎么一步步落地的（以及每一步为什么这么做）

> 写给"完全不知道为什么要这么做"的人。目的是让你脑子里有一条**主线**，
> 以后遇到新项目，也能照着这条线自己走。

---

## 一、先给你一个总的心智模型

做软件，本质是**在「脑子里的想法」和「别人真能用的东西」之间架一条链**。
这条链上每一环都可能断，所以每一环都要**能验证**。

```
想法
 └─ 需求：做什么 / 不做什么        ← 不封边就永远做不完
     └─ 最小能跑的版本              ← 先跑通，不求好看
         └─ 放到真实环境（部署）     ← 本机能跑 ≠ 别人能用
             └─ 在真实环境里验证      ← 「部署成功」≠「功能可用」
                 └─ 修掉「第一次给人看就露馅」的地方
                     └─ 坐实地基（数据不丢 / 不慢 / 出错有话说）
```

**贯穿始终的三个原则**（比任何技术细节都重要）：

1. **每一环都要有一个「判据」**——怎么知道这一步成了？
2. **判据必须是可观测的现象**——不是"我觉得应该没问题"，是"我跑出来看到了 X"。
3. **一次只推进一环，验证完再下一环**——同时改五处，出错时你不知道是哪处的错。

---

## 二、逐阶段复盘：做了什么、为什么

### 阶段 1 · 把想法收成边界（写 PRD）

**做了什么**：写 `PRD.md`——一句话说清它是什么、给谁用、解决什么问题。

**为什么**：因为「做个背调工具」这句话没有边界，**照它写代码永远写不完**。
PRD 的真正价值不在"写下来"，在于逼你说出三件事：

- **做什么**（就 4 个功能：输入公司名 → 调 LLM → 存库 → 显示）
- **不做什么**（不做登录、不做抓取、不做多语言、不做精美 UI）
- **为什么这么定**

**「不做什么」是 PRD 里最值钱的一节。** 范围不封边，你就永远在"再加一个功能"里打转。

**这次的实例**：有个看起来很香的功能——"按人名/手机号查个人信息"。我们**否决了**，理由两条：
LLM 没有真正查询能力（只会编），以及处理第三方个人信息有合规风险（PIPL/GDPR）。
这个否决 + 理由写进了「需求变更记录」——**半年后再有人提，直接翻记录，不用重新吵一遍**。

**判据**：能一句话说清"它不做什么"。

---

### 阶段 2 · 先搭「最小能跑的骨架」

**做了什么**：4 个接口（`/`、`POST /analyze`、`GET /history`、`GET /history/{id}`）
+ SQLite 存数据 + 原生 HTML/CSS/JS 页面。

**为什么是这个组合**：

| 选择 | 为什么 |
|---|---|
| FastAPI | Python 里最省事的 Web 框架，帮我们自动处理 JSON 和参数校验 |
| **SQLite** | 一个文件就是整个数据库、零安装——**当天就能跑起来**，不用先折腾数据库服务器 |
| **不用 ORM** | 项目太小，手写 SQL 反而更透明，出错时看得见是哪句 SQL |
| **原生前端** | 这一阶段的目标是"把链路走通"，不是"做好看"。UI 留到后面 |

**判据**：在自己电脑上打开，输入一个公司名，能看到生成的五段分析。

> 这一步的隐含原则：**先让它跑起来，再让它变好**。
> 很多人卡在第一步是因为想一步到位——结果三个月后还在选技术栈。

---

### 阶段 3 · 部署上线

**做了什么**：代码推到 GitHub → 在 Render 建一个 Web Service 接上仓库。

**为什么**：**本机能跑 ≠ 别人能用**。作品要给别人看，就必须有个网址。

**这一步你要理解三个概念**：

| 概念 | 什么意思 |
|---|---|
| 构建命令 | 服务器上先跑什么来装依赖（`pip install -r requirements.txt`） |
| 启动命令 | 装完怎么把服务跑起来（`uvicorn main:app ...`） |
| **环境变量** | 那些**不能写进代码**的东西（API key、数据库密码），在平台后台单独配 |

**为什么 key 不能写进代码**：代码要推到 GitHub（公开的）。
key 写进去等于把家门钥匙贴在公告栏上。所以走"环境变量"这条单独通道。

**判据**：打开网址，页面出得来。

---

### 阶段 4 · 验证「线上真的能用」（最容易漏的一步）

**做了什么**：在**线上**真的跑了一次背调。

**为什么**：这是新手最容易漏、也最坑的一步。
"部署成功"只说明**服务器把你的代码跑起来了**，**不说明功能真的能用**——
可能 key 是错的、模型名写错了、服务器连不上 LLM 服务商。

**这一步的方法很有意思**：我们一开始不知道线上到底配没配 key。
但我们发现**打开首页能返回 200** → 说明 app 启动成功了 →
而代码里"缺 key 就拒绝启动" → 所以**反推出 key 是配了的**。
这就是"用可观测现象反推内部状态"。

**判据**：线上真跑一次，出了五段分析，并且能查到这条历史。

---

### 阶段 5 · 修掉「第一次给人看就露馅」的地方

**做了什么**：两件小事——① 让 `**加粗**` 真的显示成粗体；② 点历史能展开详情。

**为什么先修这两个**：因为它们是**任何人打开就会立刻看到的破绽**：
结果区满屏星号、历史记录点了没反应。功能对不对是其次，**看起来是坏的**最致命。

**这一步的方法（也是全程的方法）**：
改代码 → **在真浏览器里跑一遍看现象** → 推送 → 回到线上核对。

顺带说一个真本事：让 `**xxx**` 变粗体，正确做法是**先把文本里的 HTML 特殊字符转义，
再做"加粗替换"**。顺序反了，LLM 返回的文本里如果带 `<script>`，就会变成真的脚本被执行
（这叫 XSS）。**这类"顺序不能反"的细节，是工程师和会打字的人的差别。**

---

### 阶段 6 · 坐实地基：让数据不再丢

**发现的问题**：PRD 的验收标准写的是"刷新后历史还在"。
但实测发现：**每次重新部署，历史记录全清空**——因为免费实例的磁盘是临时的。

**这是一个"看起来能用、其实没达标"的典型**。产品目标没达成，必须修。

**做了什么**：数据层从 SQLite 单文件 → **托管 Postgres（Neon 免费版）**。

**为什么不是"换个更大的盘"**：云平台的免费实例根本不给持久磁盘。
所以只能把数据放到**服务器之外**——这就是"托管数据库"存在的理由。

**这一步你要理解的概念链**：

| 概念 | 一句话 |
|---|---|
| 托管数据库 | 别人帮你运维的数据库，你只管连上去用 |
| 连接串（`DATABASE_URL`） | 一串"地址+用户名+密码"，程序靠它找到并登录数据库 |
| 驱动 | 让 Python 能和 Postgres 说话的库（这里用 `psycopg`） |
| 方言差异 | 换个数据库，SQL 写法有小差异（占位符 `?`→`%s`、自增主键 `AUTOINCREMENT`→`SERIAL`） |
| 两处配置 | 同一个连接串，本地放 `.env`、线上放平台后台 |

**关键动作顺序**（顺序错了会出事）：
先在平台上把 `DATABASE_URL` 配好，**再**推送新代码。
因为新代码"读不到 `DATABASE_URL` 就拒绝启动"——先推代码 = 线上直接挂。

**判据**：本地写一条记录 → 线上能看到它；重新部署一次 → 记录还在。

---

### 阶段 6.5 · 迁移暴露出来的两个新问题（这才是真实工程的样子）

把数据搬走之后，冒出两个**动手前想不到**的问题：

**问题 1 · 时区**
存时间用的是"跑代码那台机器的本地时间"。你本机是 UTC+8，Render 服务器是 UTC——
**同一张表里两条记录差 8 小时**，页面上显示成"凌晨 3 点"。
→ 修法：**统一存 UTC**，显示时由前端转成浏览者所在时区。

**问题 2 · 性能**
连一次远程数据库要 ~2 秒（TLS 握手 + 认证）。SQLite 时代开连接是本地文件、几乎免费，
所以原来"每次操作新开连接"的写法没人觉得有问题；换到远程库，**每次请求白等 2 秒**。
→ 修法：**连接池**——进程里常备几条连接，用完还回去，不再每次重新握手。

**这两个问题的意义**：它们**不是谁写错了**，而是"换了环境之后，原来的写法不再成立"。
工程里大量的时间和经验，就长在这种地方。

## 三、这套解题框架（可以直接套用到别的项目）

1. **先定边界**：做什么 / 不做什么 / 为什么。不封边就不动手。
2. **再搭最小可跑**：技术选型服从"今天能不能跑起来"，不求好看。
3. **立刻放到真实环境**：别在本地自我感觉良好。
4. **用可观测的判据验证**：不是"应该没问题"，是"我跑出来看到了 X"。
5. **修掉"第一次给人看就露馅"的**：观感坏了，功能对也没人信。
6. **坐实地基**：数据会不会丢、会不会慢、出错时有没有话说。
7. **每一步留记录**：为什么这么做、否决过什么——给三个月后的自己看。

## 四、这次用到的工具/服务，以及各自扮演什么角色

| 东西 | 角色 |
|---|---|
| Python + FastAPI | 写后端：接收请求、调 LLM、读写数据库 |
| SQLite（早期） | 最早的数据存放处，简单但会随服务器一起消失 |
| **Neon（托管 Postgres）** | 现在的数据仓库，放在服务器之外，所以不会丢 |
| psycopg | Python 和 Postgres 之间的翻译 |
| LLM API（DeepSeek 等） | 真正"生成分析"的那一环 |
| 原生 HTML/CSS/JS | 浏览器里看到的页面 |
| **Git** | 给代码拍快照（每次提交 = 一个可回退的时间点） |
| **GitHub** | 存放代码快照的地方 |
| **Render** | 从 GitHub 拉代码、跑起来、给一个公开网址 |
| curl | 不开浏览器，直接在命令行走一遍 HTTP 请求（验证用） |
| 无头浏览器（Chrome） | 不给你看界面，但在后台真跑一遍网页（验证"看起来对不对"） |

## 五、最后：什么叫"验证"（这是全篇最该带走的一条）

**验证 ≠ 我觉得。验证 = 一条别人能复核的现象记录。**

这次全程的验证长这样：

- 说"线上通了" → 附上 `curl` 返回的 JSON
- 说"粗体渲染了" → 附上无头浏览器读回的 `font-weight = 700`
- 说"数据不丢了" → 附上"本地写的一条，出现在线上"
- 说"连接池有效" → 附上改前 2.0s / 改后 0.9s 的对照数字

**下次你自己做东西时，只要做一件事就够了**：
每完成一步，问自己——**"我怎么知道它成了？把那个证据拿出来。"** 拿不出证据，就等于没做。
